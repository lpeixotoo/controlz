## Project
- **Goal:** a macOS menu-bar app that acts as a control center for the user's LG TV and LG air conditioner, **controlling every device locally — no cloud services** (D4).
- **Scope (v1):** TV power, volume/mute, input, apps, media keys, D-pad navigation. AC (power, mode, target temperature, fan) follows once a local route is chosen (T1.1).
- **Non-goals (v1):** other brands, iOS, automations/schedules, cloud APIs (LG ThinQ), App Store distribution.

## Architecture
```
SwiftUI menu-bar app (app/)                 Rust core (core/, staticlib via uniffi)
  MenuBarExtra panel + Settings   ─uniffi─▶  AcController ─ local AC server (TLS/MQTT, route per T1.1) ◀── LG AC Wi-Fi module
  @Observable @MainActor models   ◀─callbacks─ (state pushes)      TvClient ─ WebSocket (LAN) ──▶ LG webOS TV
  Keychain (Security.framework)              wol ─ UDP broadcast ──▶ TV power-on
                                            config (TOML) · ControlError · one tokio runtime
controlz CLI (cli/) ── links controlz_core directly (no FFI), same config file + Keychain service
```
- **Ownership:** Rust owns every device protocol, the AC server, config-file I/O and the domain types. Swift owns UI, the Keychain on the app side, and app lifecycle. The CLI is a thin Rust front-end over the same core, used to verify each protocol on real hardware before any UI uses it.
- **Repo layout (target):**
  - `Cargo.toml` workspace (`resolver = "3"`, shared `[workspace.package]`, `[workspace.dependencies]`, `[workspace.lints]`)
  - `core/src/`: `lib.rs`, `error.rs` (`ControlError`), `runtime.rs`, `ffi.rs` (uniffi exports), `ac/` (route-specific, shaped by T1.1), `webos/` (`transport`, `pairing`, `manifest`, `commands`, `apps`, `pointer`), `wol.rs`, `discovery.rs`; integration tests in `core/tests/` with in-process mock peers.
  - `cli/src/`: `main.rs` (clap), `config.rs`, `secrets.rs`, `ac.rs`, `tv.rs`.
  - `app/`: SwiftPM package (`Package.swift`, `Sources/Controlz/…`, `Tests/ControlzTests/`), `Generated/` (gitignored uniffi output).
  - `scripts/`: `check.sh` (all quality gates), `build-core.sh`, `bundle-app.sh`.
- **Async + threading:** the core owns one multi-thread tokio runtime (`OnceLock`). uniffi async exports (`#[uniffi::export(async_runtime = "tokio")]`) surface as Swift `async throws`. Long-lived things are uniffi Objects (`Arc`): `AcController`, `TvClient`. State changes are pushed to Swift through a foreign-implemented callback trait (e.g. `AcObserver::on_state`), which Swift hops onto `@MainActor` models.
- **Errors:** one `ControlError` enum (`thiserror` + `uniffi::Error`) with user-presentable messages. Secrets (TV client-key, any AC credentials) never appear in errors, `Debug` output or logs (`Secret` newtype with redacted `Debug`).
- **Config + secrets (D10):** non-secret config in `~/Library/Application Support/Controlz/config.toml` (read/written by the core for both CLI and app). Secrets in the Keychain under one service name (set in T0.3), accessed from Rust via `security-framework` (CLI) and from Swift via Security.framework (app).
- **AC server (if the local-cloud route wins, D12):** runs inside the app process (and `controlz ac serve` for the CLI), only while it is running. Listens on the ports the AC module expects (e.g. 443). Unprivileged processes **can bind port 443 on macOS 26** (tested 2026-11-25, uid 501). Details from T1.1.
- **Logging:** `tracing` in Rust (CLI: `tracing-subscriber`, `-v` flags), `os.Logger` in Swift; never log secrets.
- **Testing strategy:** unit tests next to the code; protocol tests against in-process mock peers (a fake webOS WebSocket server, a fake AC module client); `insta` snapshots for wire messages; fixtures use fake values only (privacy hook). Swift unit tests (Swift Testing) target view models against a fake core protocol; UI is verified by designer screenshot review.

## TV / webOS protocol
Source: `aiowebostv` (Home Assistant's library, Apache-2.0) — https://github.com/home-assistant-libs/aiowebostv ; Rust reference: https://github.com/Zakarialabib/tv-rs
- **Transport:** WebSocket. Try `wss://<ip>:3001` first (newer firmware may reject or hang on ws), fall back to `ws://<ip>:3000` (older webOS). Remember which one worked. TLS is a self-signed cert → certificate validation must be disabled for this connection only.
- **Handshake order (newer webOS):** optionally send `{"id":"hello","type":"hello","payload":{}}`; newer versions want `ssap://system/getSystemInfo` requested **before** registration.
- **Registration:** send `{"type":"register","id":"register_0","payload":{forcePairing:false, pairingType:"PROMPT", manifest:{…}, "client-key": <stored or absent>}}`.
  - First response may be `type:"response"` with `payload.pairingType:"PROMPT"` → the TV shows a prompt; wait for the next message.
  - Success: `type:"registered"`, `payload["client-key"]` → persist it (Keychain). Keep the stored key if the TV sends none.
  - `type:"error"` with a stored key while the TV is booting is transient → retry on next connect.
- **Manifest:** the well-known signed "LG Remote App" manifest (appId `com.lge.test`, signature + `signed` block, permission list). Copy it from `aiowebostv/handshake.py` (Apache-2.0, keep attribution). **Newer firmware rejects the signature:** on `type:"error"` retry once with an *unsigned* manifest (remove `signatures`, merge `signed.permissions` into `permissions`, drop `signed`).
- **Requests:** `{"id":"<unique>","type":"request","uri":"ssap://<endpoint>","payload":{…}}`; match responses by `id`.
- **Endpoints (ssap://…):** `audio/volumeUp`, `audio/volumeDown`, `audio/setVolume {volume}`, `audio/getVolume`, `audio/setMute {mute}`, `audio/getStatus`, `system/turnOff`, `system/turnOn`, `system/getSystemInfo`, `com.webos.applicationManager/listLaunchPoints`, `com.webos.applicationManager/launch {id}`, `com.webos.applicationManager/getForegroundAppInfo`, `tv/getExternalInputList`, `tv/switchInput {inputId}`, `tv/channelUp`, `tv/channelDown`, `media.controls/play|pause|stop|rewind|fastForward`, `com.webos.service.tvpower/power/getPowerState`, `com.webos.service.tvpower/power/turnOffScreen|turnOnScreen`, `system.notifications/createToast {message}`.
- **Buttons (D-pad, OK, Back, Home…):** request `ssap://com.webos.service.networkinput/getPointerInputSocket` → `payload.socketPath` (a ws/wss URL); open a second WebSocket to it and send text frames `type:button\nname:<NAME>\n\n` (names: `UP`, `DOWN`, `LEFT`, `RIGHT`, `ENTER`, `BACK`, `HOME`, `MENU`, `EXIT`, …).
- **Power on:** the socket is down when the TV is off → use Wake-on-LAN (magic packet to the TV's MAC, UDP broadcast ports 9/7). Requires the TV setting "Turn on via Wi-Fi" / "Mobile TV On".
- **Power off:** `system/turnOff`; the response may never arrive while shutting down → don't wait for it.

## Home network
- DHCP hands out the **router as the DNS server** (`ipconfig getpacket en0`, 2026-11-25), so the AC will resolve names through the router. The Mac itself is manually set to 8.8.8.8.
- The router is an ISP-supplied box with a web admin page (user has access). Its identifiers are deliberately **not recorded anywhere** (user request, 2026-11-25).
- **Router capabilities** (source: user screenshots of the admin UI, 2026-11-25):
  - DHCP server on; a **"specific DNS server" option** that changes the DNS server handed out by DHCP (currently off). It is network-wide, not per device.
  - **DHCP reservations** (hostname/MAC → IP): use them to pin the TV, the AC and whichever machine hosts the local AC server.
  - Port forwarding, DMZ, UPnP, DDNS pages exist. **No local DNS host-override / static-DNS page** was seen.
- Consequence for the AC: overriding one hostname (needed by ThinQ1 modules, which always call an LG domain) requires running **our own DNS resolver** on the LAN and pointing the router's "specific DNS server" at it — then the whole home's DNS depends on that box being up. A ThinQ2 module can be given our own hostname instead (see below), which may avoid any router change.
- The earlier "router doesn't answer DNS/HTTP" test was invalid: macOS Local Network permission was blocking the terminal (EHOSTUNREACH on every LAN address, internet fine). (corrected 2026-11-25)
- Public wildcard DNS (e.g. `<ip-with-dashes>.sslip.io`) resolves to LAN addresses via 8.8.8.8 (tested 2026-11-25). **The router's DNS forwards these answers too (no DNS-rebind filtering; `dig @router`, 2026-11-25)** → a ThinQ2 module can be pointed at a server on the Mac **without any router change**.

## AC — local control options (decided in T1.1: see T1.1 findings)
- **Matter (local IP, two-way):** only some newer LG ACs ship Matter support — check the model. A Matter device can join several fabrics (multi-admin), so it could stay in ThinQ/Apple Home and also be commissioned by Controlz. On macOS, candidates are Apple's `Matter.framework` (`MTRDeviceController`, own fabric) or HomeKit (available to Mac Catalyst apps only); a Rust controller (`rs-matter`) is less mature. **All unverified — T1.1 confirms.** (corrected 2026-11-26: irrelevant for our AC, which has no Matter; see T1.1 findings.)
- **IR blaster (local, one-way):** a Wi-Fi IR blaster (e.g. Broadlink RM4 mini, local UDP protocol, see `python-broadlink`) replays the AC remote's codes. Works with any model; no state readback (Controlz keeps its own assumed state). Needs extra hardware.
- **Not available:** a documented local Wi-Fi API on LG ACs; Bluetooth control.
- **For S4NQ09WA51A (2020, LCW-003 module): Matter support is unlikely** — Matter 1.0 shipped in late 2022, after this unit. Unverified; T1.1 confirms. (corrected 2026-11-26: confirmed no Matter, now or by firmware; see T1.1 findings.)
- **Local ThinQ cloud replacement — `rethink` (most promising, partly verified):** https://github.com/anszom/rethink (GPL-2.0, ~400★, active Nov 2026). Source: its README, wiki and `rethink-setup.ts`, read 2026-11-25.
  - How: while the AC is in SoftAP mode, a computer joins the `LG…` network and talks TLS to port 5500 on the module's fixed SoftAP gateway address (LG default, listed in `rethink-setup.ts` usage text). ThinQ1 modules: XML `mTosp` messages (`deviceinfo`, then `apinfo` with base64 SSID/password and a fake `regionalCode`). ThinQ2 modules: JSON `setDeviceInit` … plus an RSA public key. The AC then joins the home Wi-Fi and connects to a **local server pretending to be LG's cloud** (MQTT over TLS) instead of LG.
  - Two-way: state readback and control, no extra hardware, no cloud. Wall-mounted LG ACs (ThinQ model `RAC_056905_WW`, "DualCool family IDUs") have its highest support level; whether S4NQ09WA51A reports that model, and whether LCW-003 is ThinQ1 or ThinQ2, is **unverified** (the SoftAP `deviceinfo` reply would tell). (corrected 2026-11-26: our module speaks the ThinQ2 JSON setup protocol (probe); model `RAC_056905_WW` is inferred from sources, not read from the device. See T1.1 findings.)
  - Requirements: an always-on server on the LAN (rethink is Node.js; listens on 443), **DNS on the LAN redirecting the AC's cloud hostname to that server** (the Wi-Fi module has no mDNS), its own MQTT broker. After provisioning, the AC no longer talks to the official ThinQ app (re-provisioning with the ThinQ app undoes it).
  - For Controlz: either run rethink as a separate service and talk MQTT to it, or reimplement the needed server side in the Rust core (clean-room from the wiki; copying rethink code would pull in GPL-2.0). To decide in T1.1.
- **Possible fourth route (unverified):** community ESP32/ESPHome projects that replace or tap an LG AC's Wi-Fi module / indoor-unit serial bus for local two-way control. Hardware modification of a 220 V appliance (warranty and safety risk). T1.1 checks whether any project supports this model. (corrected 2026-11-26: no project lists this model; see T1.1 findings.)

### T1.1 findings (2026-11-26)
Sources: desk research plus a read-only probe of the AC's SoftAP (TCP/TLS only, no setup commands, no Wi-Fi credentials). Probe values → `docs/local.md`. rethink was read for facts only (wiki + code at commit `8e3db5d`, 2026-11-21); nothing copied. **Clean-room rule for T1.2+:** implementers work from the rethink wiki, our own captures and MIT/0BSD references only — never the rethink (or rethink-rs) source.

**Routes**
- **Matter: no.** No LG listing or announcement; a firmware upgrade to Matter is implausible on this 2015 module (inference). LCW-003 is a Qualcomm QCA4010 module (4 MB flash), FCC ID BEJ-LCW003, granted 2015-10-26 (deviwiki LG_LCW-003; fccid BEJ-LCW003). CSA's certified-product search (2026-11-26) lists no LG air conditioner, only LG sensors, a plug and the ThinQ app as a Matter *controller* (CSA23005SWC60056-M2, Matter 1.0, 2023-03-07). LG's ThinQ ON hub reaches older appliances through the cloud, not by Matter on the appliance.
- **Local LG-cloud stand-in (rethink-style), ThinQ2: works for our unit.**
  - *ThinQ1 vs ThinQ2, from the probe:* TLS on port 5500 answers, port 9000 is closed. ThinQ1 RAC "Whisen" modules (QCA4002) are set up over port 9000 (rethink issue #70, PR #194). A ThinQ1 XML `mTosp` `deviceinfo` frame got the JSON reply `{"cmd":"ping","type":"request"}` (`ping` is a JSON setup-protocol command, rethink wiki SetupProtocol:JSON), and then the module closed the connection. The SoftAP gateway address matches the one in that wiki page. → **ThinQ2, JSON setup protocol.**
  - *Sources agree:* QCA4010 runs ThinQ2 on other LG products (rethink issue #100, RC90U2_WW). S4NQ09WA51A, with the same full model code as ours, was reported working with homebridge-lg-thinq-ac in Oct 2021 (issue #97). At that date the plugin rejected anything but `thinq2` (`src/platform.ts:216` @429d10a). rethink PR #349 (2026-11-20, same reporter) adds a capture from a cooling-only 9,000 BTU split on the ThinQ2 `RAC_056905_WW` TLV class.
  - *Model:* **`RAC_056905_WW`** (confirmed by `getDeviceInfo`, T1.3, 2026-11-27). On cooling-only units Auto is mode 3, not 6 (rethink PR #340).
  - *Setup protocol (SoftAP, TLS to port 5500):* concatenated JSON objects with no delimiter (needs a streaming splitter). Commands are `setDeviceInit`, `getDeviceInfo {publicKey (PEM, no indentation), constantConnect:"Y", optional apiServer/mqttServer}` → `{modelName, uuid, softwareVer, encrypt_val, …}`, `setCertInfo {otp, svccode, svcphase:"OP"}`, `setApInfo {ssid/password base64}` and `releaseDev`. Without `constantConnect:"Y"` the module closes the connection after each command. The module also sends `ping` requests; answering `pong` is probably expected (unverified). (corrected 2026-11-27, T1.3 device run: `getDeviceInfo` alone, without `setDeviceInit` first, got a full reply; no `ping` was seen during that short run; Controlz answers pings with `{"type":"response","cmd":"pong"}`, still unverified on the device.) (rethink wiki SetupProtocol:JSON, enrolling-newer-firmware)
  - *Local cloud side:* `GET /route` → `{resultCode:"0000", result:{apiServer, mqttServer}}` (the device accepts any HTTPS cert here). `GET /route/certificate[?name=common-server|aws-iot]` returns the CAs the device then trusts. `POST /device/<uuid>/certificate` takes a CSR and returns the signed client cert. Then MQTT over TLS (client cert, clientId = uuid): the device publishes `preDeploy`/`deploy` on `clip/provisioning/devices/<uuid>`, the server answers `completeProvisioning` on `lime/devices/<uuid>` with the topic names, and the device sends `completeProvisioning_ack`. State comes as `device_packet` (hex TLV) on the message topic. Commands go as `packet` (hex TLV) to `lime/devices/<uuid>`. Use the default topic names: a non-default `topic_prov` is stored in flash and can break later setups with the official cloud. Ports 443 and 8883 (some devices ignore non-default ports). (rethink wiki Thinq2CloudProtocol, TLVProtocol, Appliance:RAC_056905_WW, Installing-rethink-cloud)
  - *Implemented in T1.4* (`core/src/ac/cloud.rs`): `CloudSession::start(&CloudConfig{bind, port, advertised_host}, &Pki, uuid)` → `CloudServer` (`local_addr`, `shutdown().await`, aborted on drop). The bind address must not be unspecified (loopback is allowed). The advertised host is an IP (IPv6 written in brackets in the URLs) or a hostname. Advertised ports are always 443/8883. Request body: the raw PEM CSR. Replies use the wiki shapes (`certificatePem` for both certificate endpoints). **Error replies are our own invention, not LG's:** HTTP 400/403/404 with `{"resultCode":"0400"|"0403"|"0404","result":null}`. Limits: 8 connections, 10 s TLS handshake, 10 s header read, 10 s body read, 16 KiB body, 60 s per connection. Logs show `/device/***`, the reason, the method and the body length, never the uuid or the CSR. (source: T1.4)
  - *Implemented in T1.5* (`core/src/ac/mqtt.rs`, `tls::mqtt_acceptor`): `MqttSession::start(&MqttConfig{bind, port}, &Pki, uuid)` → `MqttBroker` (`local_addr`, `next_event().await` → `DeviceEvent::{Connected, Provisioned{kind: PreDeploy|Deploy}, DevicePacket{hex}, Disconnected}` on a 64-slot queue, `send_packet(hex)` → `{did, mid, cmd:"packet", type:1, data:hex}` on `lime/devices/<uuid>`, `shutdown().await`). In-crate MQTT 3.1.1 subset (QoS 0/1; QoS 2 closes the connection). TLS requires a client cert issued directly by the client CA with clientAuth (store = client CA only, depth 1, `X509PurposeId::SSL_CLIENT`; a mutation test showed the purpose is what refuses a serverAuth-only cert). CONNECT is accepted only if cert CN == clientId == uuid (else CONNACK 0x05); one device session, a new valid CONNECT takes over. `completeProvisioning` publishes **LG's own topic names** (user decision 2026-11-27, option a): `message` = `$aws/rules/clip_http_action_rule/clip/devices/<uuid>/message`, `provisioning` = `$aws/rules/clip_provisioning_rule/clip/provisioning/devices/<uuid>`, plus `host:"message"`, `provisioningType`, `deployInterval:600`. **TLS / certificates (all routes that talk to the module)**
- The module's TLS stack is **TLS 1.2 only with CBC-SHA suites**: the probe negotiated `ECDHE-RSA-AES256-SHA` with a relaxed OpenSSL profile, while TLS 1.2 AEAD-only and TLS 1.3-only both got a `handshake_failure` alert. Its 5500 certificate is a self-signed, shared RSA-1024 cert (probe; SetupProtocol:JSON "same for every device"). rethink needs the same legacy profile on its servers for newer modules (TLS 1.2, legacy ciphers at `@SECLEVEL=0`, legacy renegotiation flags; enrolling-newer-firmware §3).
- **rustls cannot be used**: it has no CBC suites, and its verifiers reject RSA keys under 2048 bits. Use the **`openssl` crate with `vendored`** (static OpenSSL, independent of macOS's LibreSSL and Homebrew) for the setup client (to port 5500) and for the HTTPS and MQTTS servers. Profile: TLS 1.2 min/max, `ECDHE-RSA-AES256-SHA:ECDHE-RSA-AES128-SHA:AES256-SHA:AES128-SHA@SECLEVEL=0`. The same crate covers X.509: RSA-2048 CA and server keys (ECDHE-*RSA* suites need RSA certs), SAN = our hostname, and signing the device's CSR. native-tls (Security.framework) supports CBC but has no client-cert or CSR API and is deprecated on Apple platforms, so it is not used.
- Implemented in T1.2 (`core/src/ac/tls.rs`, `core/src/ac/pki.rs`): `server_acceptor` (TLS 1.2 min = max, the cipher list above, `ALLOW_UNSAFE_LEGACY_RENEGOTIATION`) and `module_connector` (same, plus `SSL_OP_LEGACY_SERVER_CONNECT` and no certificate verification, since the module's cert is shared and self-signed). OpenSSL 3 no longer includes `LEGACY_SERVER_CONNECT` in `SSL_OP_ALL`, and the `openssl` crate 0.10.82 has no named flag for it: it is set via `SslOptions::from_bits_retain(openssl_sys::SSL_OP_LEGACY_SERVER_CONNECT)` (0x4). In-process tests: a client restricted to `ECDHE-RSA-AES256-SHA` negotiates it over TLS 1.2 and verifies our CA and SAN; a TLS 1.3-only client is refused. `Ca::sign_csr` verifies the CSR's own signature and copies only its subject and public key (clientAuth EKU, random 127-bit serial, SHA-256). (source: T1.2 implementation and tests, 2026-11-26) (corrected 2026-11-26, T1.2 review: `tls::accept`/`tls::connect` bound the handshake with `HANDSHAKE_TIMEOUT` = 10 s and map a timeout to `ControlError::Network`.) (corrected 2026-11-26, T1.4: `server_acceptor` now uses the ECDHE-only `SERVER_CIPHERS` and `NO_RENEGOTIATION`; see the next line.)
- Changed in T1.4 (`core/src/ac/tls.rs`, `core/src/ac/pki.rs`, 2026-11-26):
  - `server_acceptor` now offers only `SERVER_CIPHERS` = `ECDHE-RSA-AES256-SHA:ECDHE-RSA-AES128-SHA@SECLEVEL=0` and sets `SslOptions::NO_RENEGOTIATION` instead of `ALLOW_UNSAFE_LEGACY_RENEGOTIATION`. `module_connector` keeps `MODULE_CIPHERS` and the legacy flags. Both old settings stay documented fallbacks until T1.9 checks the device. Tests: a client offering only `AES256-SHA` is refused; a client renegotiation (test-only FFI `SSL_renegotiate`) is refused. (source: T1.4 tests)
  - OpenSSL 3.x servers already refuse client-initiated renegotiation unless `SSL_OP_ALLOW_CLIENT_RENEGOTIATION` (bit 8, no binding in `openssl-sys` 0.9.118) is set and `SSL_OP_NO_RENEGOTIATION` is clear (`RENEG_OPTIONS_OK`, `ssl/statem/statem_srvr.c`, openssl-src 300.6.1). So T1.2's `ALLOW_UNSAFE_LEGACY_RENEGOTIATION` never enabled client renegotiation on our server; `NO_RENEGOTIATION` makes the refusal explicit. Inference, unverified on the device: a module without RFC 5746 still completes the first handshake, so the fallback flag is unlikely to be needed. openssl-sys 0.9.118 has no `SSL_renegotiate` binding either; the test declares it itself. (source: openssl-src 300.6.1 sources, `ssl.h.in`; T1.4 control test `renegotiation_works_when_allowed`)
  - **Two CAs** in the PKI dir (D20 route): `ca.pem`/`ca.key` is the server CA (signs only `server.pem`; it is what `/route/certificate` returns) and `client-ca.pem`/`client-ca.key` is the client CA (signs only module CSRs; never sent to the module). Both are RSA-2048 with `basicConstraints` `CA:TRUE, pathlen:0`. The client CA is generated when missing, and a bad client-CA pair is a hard error, like the server CA. If the module rejects a client cert from a different CA than the one it was given (T1.9), fall back to one CA and record why here. (source: T1.4)
  - `Ca::sign_csr(csr, expected_cn, days)` accepts `days` in 1..=825, RSA keys of 2048 to 8192 bits or EC P-256 only, a CSR whose own signature verifies, and a subject with exactly one CN equal to `expected_cn`. The key is checked before the signature, so a huge RSA key costs nothing. The cloud issues 825-day client certs. `server_is_current` now treats a `verify()` error (e.g. an EC CA key against an RSA signature) as "not current" and re-issues. (source: T1.4)

**DNS plan (ThinQ2, server on this Mac, D12)**
- *Ongoing:* `/route` returns `https://<mac-ip-with-dashes>.sslip.io:443` and `ssl://<same>:8883`. This must be a DNS name with non-zero TTL, not an IP or a `.local` name (Installing-rethink-cloud). It resolves through the router (KB: Home network), so **no router change is needed**. Requirements: a DHCP reservation for the Mac, because its IP is baked into the hostname (and into the server cert SAN). Every lookup also depends on internet DNS and the public sslip.io service (open question vs D4, see Open questions). If either changes, re-run setup, or use a user-owned domain with an A record.
- *One-time setup call to `common.lgthinq.com/route` (firmware-fixed):* three options.
  1. **Pass `apiServer`/`mqttServer` in `getDeviceInfo`.** No router change. Whether this skips `common.lgthinq.com` is unverified (rethink wiki TODO). If it doesn't, the module asks LG's real server once and setup fails harmlessly (re-run setup).
  2. **Temporary resolver on the Mac** (answers `common.lgthinq.com` with the Mac's address, forwards everything else) plus router "specific DNS server" = Mac, **only for the few setup minutes**, then switch it back. The whole home depends on the Mac's DNS during that window. The module gets a fresh DHCP lease after `releaseDev`, so it picks up the setting. Binding UDP 53 unprivileged on macOS 26 is unverified (443 works).
  3. **Recommended:** try 1 first, with 2 ready as the fallback. The router change is a user action, approved each time.
- ThinQ1 would have needed a permanent `<regionalCode>.lgthinq.com` override (ports 46030/47878) and so a permanent own resolver. Not applicable.

**Run rethink as a service vs clean-room Rust**
- *rethink as a service:* GPL-2.0 is fine for a separate process we don't distribute or link. But it needs Node.js (not installed; D15) or Docker, plus an external MQTT broker for its HA-facing side (e.g. mosquitto). It also needs the legacy-TLS patch (enrolling-newer-firmware §3). Controlz would then talk to it over MQTT. That is three moving parts outside the app, against the in-app server this recommendation prefers (D12 only requires the server to run on this Mac).
- *Clean-room Rust in `controlz_core`:* in-process, one binary, no GPL. cargo-deny forbids GPL deps, and copying rethink code would make Controlz a derivative work. Write it from the wiki's protocol descriptions, our own captures and the MIT reference paoloantinori/local_smarthinq1 (ThinQ1, Python). BluSyn/rethink-rs is GPL-2.0, so don't read it for code. **Chosen.**

## AC / ThinQ Connect API (reference only — not used, see D4)
Source: LG's official SDK `pythinqconnect` (Apache-2.0) — https://github.com/thinq-connect/pythinqconnect ; PAT docs — https://thinq.developer.lge.com/en/cloud/docs/thinq-connect/PAT-en/
- **Cloud only.** There is no documented local API for LG ACs. Expect seconds of latency.
- **Auth:** Personal Access Token created by the user at https://connect-pat.lgthinq.com (sign in with the ThinQ account → Add new token → choose scopes). Stored in Keychain.
- **Base URL:** `https://api-<region>.lgthinq.com/` where region is `kic` / `aic` / `eic` chosen by the account's country (mapping table in `thinqconnect/country.py`; e.g. US and BR → `aic`; KR, AU → `kic`; most of Europe/Middle East/Africa → `eic`). Verify the user's country against the table.
- **Headers on every request:**
  - `Authorization: Bearer <PAT>`
  - `x-country: <ISO country code>`
  - `x-message-id: <base64url(uuid4 bytes) without padding, 22 chars>`
  - `x-client-id: <uuid, stable across restarts — generate once and persist>`
  - `x-api-key: v6GFvkweNo7DK7yD3ylIZ9w52aKBU0eJ7wLXkSR3` (public program key shipped in LG's SDK; identifies the API, not the user)
  - `x-service-phase: OP`
  - control calls also send `x-conditional-control: true`
- **Endpoints:** `GET devices` (list), `GET devices/{id}/profile` (capabilities), `GET devices/{id}/state`, `POST devices/{id}/control` (JSON body). Push/events via `POST event/{id}/subscribe` + MQTT (later phase).
- **Responses:** success → JSON with the payload under `response`. Error → `{"error":{"code":"<4 digits>","message":…}}`. Useful codes: `1103` invalid token, `1218` invalid token again, `1306` exceeded API calls, `1222` device not connected, `2301`–`2305` command not supported in current state (e.g. `2304` when powered off), `2209` device response delay, `2210` retry request.
- **Device type** for ACs: `DEVICE_AIR_CONDITIONER`.
- **State/control resources (AC):**
  - power: `{"operation": {"airConOperationMode": "POWER_ON" | "POWER_OFF"}}`
  - mode: `{"airConJobMode": {"currentJobMode": "COOL" | "HEAT" | "AIR_DRY" | "FAN" | "AUTO" | …}}`
  - fan: `{"airFlow": {"windStrength": "LOW" | "MID" | "HIGH" | "AUTO" | …}}` (some models use `windStrengthDetail`; check the profile)
  - temperature — **two shapes exist, pick by what the device's state/profile contains:**
    - `temperature` (object): `{currentTemperature, targetTemperature, unit}`; control `{"temperature": {"targetTemperature": 22, "unit": "C"}}`
    - `temperatureInUnits` (array, one entry per unit): `[{unit:"C", currentTemperature, targetTemperature, …}, {unit:"F", …}]`; control `{"temperatureInUnits": {"targetTemperature": 22, "unit": "C"}}`
  - others available: `powerSave.powerSaveEnabled`, `display.light`, `windDirection.rotateUpDown`, `timer`, `sleepTimer`, `airQualitySensor`, `filterInfo`.
- **Profile format:** `profile.property.<resource>.<key> = {"type": "enum"|"range"|"boolean", "mode": ["r","w"], "value": {"r": [...], "w": [...]}}` (range values carry `min`/`max`/`step`). Writable mode/fan lists and temperature limits come from here; don't hardcode them. Multi-unit devices may have `property` as a list keyed by location.

## macOS platform
- Local network access: apps that reach LAN devices need `NSLocalNetworkUsageDescription` in Info.plist, and the user grants "Local Network" in Privacy & Security. Without it, connections and discovery fail silently. (Apple TN3179: https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy.md)
- The multicast entitlement is not required on macOS.
- Menu-bar-only app: `LSUIElement = YES`; SwiftUI `MenuBarExtra` with `.menuBarExtraStyle(.window)` gives a popover-like panel.
- Secrets in Keychain (`kSecClassGenericPassword`).
- Keychain layout (D10, T0.3): generic passwords with service **`dev.controlz`** and account = secret name (today only `tv.client-key`). Tests use service `dev.controlz.test`. Written via `security_framework::passwords::{set,get,delete}_generic_password`; `errSecItemNotFound` (-25300) means "not set". Code: `cli/src/secrets.rs`. (source: T0.3 implementation, 2026-11-25)
- Config file (D10, T0.3): `$HOME/Library/Application Support/Controlz/config.toml`, path from `std::env::home_dir()`; read/written by `controlz_core::Config` (`core/src/config.rs`) so the app reuses it. Keys `tv.host`, `tv.mac` (MAC normalised to lowercase colon form); `config set` rejects unknown keys; unknown keys/tables in the file are kept on load → save and logged as a warning (names only), so older builds keep newer settings; saves go through a pid-unique temp file + rename (temp removed on failure; concurrent writers: last one wins, no lock). `config secret set` reads only from piped stdin and refuses a terminal (it would echo). (source: T0.3 implementation, 2026-11-25)
- AC PKI files (T1.2): `$HOME/Library/Application Support/Controlz/pki/` (dir 0700), `ca.pem` + `ca.key` (our RSA-2048 CA, 10 years) and `server.pem` + `server.key` (RSA-2048 leaf, DNS SAN = the server hostname, 825 days). Keys are PKCS#8 PEM in 0600 files; every file is written via a pid-unique temp file (created with its final mode) + rename, key before cert. `Pki::load_or_create(dir, hostname)` reuses existing files, generates whatever is missing and re-issues the server cert when its SAN lacks the hostname (corrected 2026-11-26, T1.2 review: also when the CA was just generated, the cert does not verify against the CA, it expires within 30 days, or the server pair is unparsable/mismatched (I/O errors such as permission denied still fail), e.g. a new key next to the old cert after a crash mid re-issue; a bad CA pair stays a hard error, since silently regenerating it would orphan enrolled modules; key files are re-chmodded 0600 on every load). Private keys are not in the Keychain (user choice in the T1.2 brief, option A); in memory they only leave `pki.rs` as `Secret`, and `Debug` masks them. Tests use a temp dir, never the real path. (source: T1.2 implementation, 2026-11-26)

## Gotchas
- **AC server security** (T1.2 discussion, 2026-11-26): our CA is trusted only by the AC — **never add it to the macOS trust store / System keychain** (it could then be used to fake websites). Keep OpenSSL current: updates are manual (D19), `cargo deny` advisories fail the gate when a RustSec advisory lands. **Never forward ports 443/8883 on the router**; the servers are LAN-only. Biggest residual risks: the SoftAP setup window (the module's cert is shared and self-signed, so a nearby attacker could impersonate it and read the Wi-Fi password sent by `setApInfo`), and a bug in OpenSSL (C) letting a LAN attacker run code as the user. Mitigations are planned in T1.4, T1.5, T1.9 and T7.4.
- An app that **listens** for connections (the AC server) triggers the macOS application-firewall "accept incoming connections" prompt when the firewall is on. Ad-hoc signed builds change identity every build → the prompt can repeat during development. Stable signing (T7.3) fixes it.
- **One CSR per provisioning session (T1.4, kept strict by the user 2026-11-26):** `POST /device/<uuid>/certificate` signs at most once per `CloudSession`. If the module sends its CSR, the signed reply is lost (TLS drop, timeout) and the module retries, the retry gets 403 and provisioning stalls. The way out is to restart the session (a new `CloudSession`). T1.9 follow-up: watch for retries on the device; if they happen, consider allowing a re-sign of the same public key. (source: T1.4 brief Q4)
- The GitHub repo is public. A pre-commit hook (`.githooks/pre-commit`, enabled with `git config core.hooksPath .githooks`) blocks LAN IPs, MAC addresses, personal emails and `thinqpat_` tokens; mark obvious fakes with `privacy:allow`.
- ~~`core/` contains a **partial, uncompiled** start from before the workflow existed: `Cargo.toml`, `uniffi-bindgen.rs`, `src/lib.rs` (declares `thinq`/`webos` modules that don't exist yet), `src/wol.rs` (Wake-on-LAN + tests). Kept (D7); `reqwest` and the `thinq` module are no longer needed (D4).~~ (corrected 2026-11-25: T0.2 made `core/` compile inside the root workspace; `thinq` removed, `webos` is a stub, `ControlError` lives in `src/error.rs`.)
- The TV client-key is a secret: never in code, fixtures, logs or docs.
- Keychain items written by the unsigned/ad-hoc-signed `controlz` CLI land in the login keychain with an access list tied to that binary. A rebuilt binary (new identity) or the app reading the same item may trigger a "wants to use your confidential information" prompt until signing is stable (T7.3). The data-protection keychain would need entitlements, which a plain CLI does not have. (source: Apple Keychain Services docs on legacy keychain ACLs; not yet observed here, the Keychain test is `#[ignore]`d, 2026-11-25)
- The TV gets its IP by DHCP; the router supports DHCP reservations — the user should reserve the TV's (and later the AC's and the AC-server host's) IP so configured addresses stay valid (until SSDP discovery, T7.1).
- macOS Local Network permission applies to every app that reaches the LAN — including the terminal running the CLI and the user's browser. Denied → instant "No route to host" while the internet still works.
